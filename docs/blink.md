# 블링크: 눈동작을 화면과 게임의 입력으로

손을 쓰기 어려운 순간에도 휴대폰을 조작하려고 만들었습니다. **BlinkRoll은 깜빡임으로 세로 스크롤, BlinkPage는 가로 넘김, BlinkGame은 시선을 이용한 좌우 이동**으로 확장해 출시했습니다. 출시한 입력 기능과, 촬영·거리 변화에 강한 공통 시선 모델 연구는 구분합니다.

직접 사용하며 문제·가설·채택 기준을 정했습니다. 구현·학습·검증과 문서화에는 AI 코딩 도구를 활용하고 실제 입력과 로그로 결과를 판단했습니다. Kotlin/CameraX·MediaPipe·Android 접근성, Rust, Unity/C#, Python·PyTorch/CUDA를 사용했습니다. 2026년 10월 15일까지의 기록입니다.

## 1. 감도를 조절해도 의도한 깜빡임을 놓쳤다

밝기·거리·사용자가 달라지면 같은 시간 기준이 맞지 않았습니다. 오작동을 막는 조건을 더하면 정상 입력도 막혔습니다. 저는 빠른 V형과 느린 V형이 같은 동작이라면 같은 뜻으로 읽어야 한다고 제안했습니다.

눈이 닫히고, 필요하면 유지한 뒤 다시 열리는 전체 파형을 하나의 사건으로 해석했습니다. 관측이 끊긴 시간을 임의로 채우지 않고 유지·재열림 관계를 확인했습니다. 개인 보정은 열린 눈 크기 같은 입력 기준에 사용하되, 이전의 긴 동작이 다음 동작의 의미까지 바꾸는 경로는 제한했습니다.

같은 파형의 순서와 시각을 바꾸는 회귀 검사를 남기고, 임시 시간 조건 대신 유지 구간 판정을 고쳤습니다. 자연 깜빡임과 의도 입력이 같은 파형이면 완전히 구별하지 못할 수 있습니다.

## 2. 눈 감김 표시가 나와도 화면은 안 움직였다

카메라 미리보기, 눈 상태 인식, 동작 해석, 접근성 명령, 실제 화면 이동은 다른 단계였습니다. 앱을 확장하면서 같은 파일을 복사해도 제품별 실행이 달라지고, 시험용 재생기와 실제 판정 규칙이 어긋나는 문제도 발견했습니다.

공통 눈동작 해석과 Roll·Page·Game의 행동을 나누고, 한 사건이 한 행동만 만들도록 추적했습니다. 게임에서는 Unity가 카메라 판단을 다시 만들지 않고 공통 입력을 행동으로 받게 했습니다. 준비·일시정지·재개 예약도 카메라 소유 상태로 관리해 연습 화면이 외부 제어를 가로채지 않도록 했습니다.

Roll의 잠금 후 재개를 실기기에서 확인하고, 내부 시험의 동일 AAB를 재빌드 없이 출시로 승격했습니다. 한 앱의 성공을 다른 앱에 확대하지 않았으며 OS 강제 종료나 모든 제조사 조합까지 검증한 것은 아닙니다. 미완성 게임 기능은 출시판과 분리했습니다.

## 3. 인식을 더 자주 하면 오래된 프레임이 쌓였다

다른 영상 앱과 함께 쓰면 버벅임과 발열이 있었습니다. 단순히 추론 횟수를 줄이면 중요한 눈동작을 놓칠 수 있어, 입력 품질을 유지하면서 불필요한 대기를 줄이는 쪽을 먼저 조사했습니다.

Roll은 프레임 복사 전부터 완료까지 작업 예산을 적용해 실행 하나와 후속 하나만 남겼습니다. 같은 비용을 준 합성 부하 시험에서 최대 작업 대기가 **503ms에서 67ms**로 줄었습니다. 실제 눈 인식 속도나 영상 앱 전체의 개선율과는 다른 수치입니다.

Rust 영상 변환은 크기가 같은 회전의 불필요한 보간을 줄였습니다. 출력 일치와 한 기기의 연산 시간 감소를 확인했습니다. 장시간 발열·배터리나 구형 기기의 인식 실패 해결은 별도 과제입니다.

## 4. 연구 데이터를 믿기 전에 무엇을 기록했는지 봤다

촬영을 바꾸면 같은 중앙도 좌우로 오인했습니다. 얼굴 각도를 학습하는지 확인했더니 과거 좌표 자료에는 필요한 얼굴 자세 추정값이 빠져 있었습니다. 저장 영상은 확대돼 있었고 실제 눈 영역의 원래 해상도도 더 작았습니다.

눈 영상과 같은 시각의 얼굴 자세 추정·누락을 저장하고 상대 눈 크기와 기기 자세를 구분했습니다. 인접 프레임만 잘 맞히는 결과를 피하려고 평가할 촬영 하나를 학습에서 통째로 제외했습니다. 고정 조건을 먼저 확인하고 정밀 좌표에서 좌·중립·우 등 축별 문제로 범위를 좁혔습니다.

관측 조건을 비교할 자료는 갖췄지만, 얼굴 추정값은 물리적 정답 각도가 아니고 상대 눈 크기는 cm 단위 거리가 아닙니다. 고정된 단일 사용자 자료의 결과를 새 사용자 전체의 정확도로 발표하지 않았습니다.

## 5. 눈동자 외의 단서는 도움이 될까

아래를 볼 때 눈동자가 눈꺼풀에 가려지는 관찰에서 눈꺼풀 모양으로 상하를 보자고 제안했습니다. 얼굴로 대략 추정한 뒤 눈으로 수정하는 방식, 주시안 가설에서 출발해 양쪽 눈 정보를 너무 일찍 평균하지 않는 방식도 비교했습니다. 흰자와 화면 밝기를 단서로 보자는 가설 역시 실험의 출발점이었습니다.

눈꺼풀 모델은 한 반복 촬영의 상·중·하 구분이 좋아져도 작은 눈·자세 변경에서는 나빠졌습니다. 얼굴 우선 모델과 양안 분리 모델도 조건별 이득과 퇴행이 공존했습니다. 따라서 더 높은 숫자 하나로 기본 모델을 교체하지 않았습니다.

눈 주변 영상은 근육 전기 신호가 아니고 밝은 픽셀도 흰자 정답은 아닙니다. 의학적 주시안 판정이나 범용 시선 추정의 완성으로 쓰지 않고, 가설과 검증 범위를 함께 기록했습니다.

## 6. 덜 흔들려도 더 오래 틀릴 수 있었다

시선 점이 튀어 포인터를 밀어 움직이는 제어와 필터를 비교했습니다. 움직임이 줄어도 목표 위치를 맞힌다는 뜻은 아니었고, 평균을 강하게 내면 반응이 늦거나 정상 입력이 새로 누락됐습니다.

같은 모델 출력을 원본·이동평균·EMA·One Euro에 넣어 흔들림뿐 아니라 추가 지연·미실행을 비교했습니다. 상태 전이 후보는 한 개발 기록의 일치도가 **82.01%에서 86.04%**로 올랐지만, 지속 오판은 **12.039초에서 15.552초**로 늘었습니다. 저는 체감 차이가 없다는 결과를 반영해 기본 모델 채택을 보류했습니다.

흔들림·위치 편향·촬영 변화와 오판 회복을 따로 보기 시작했습니다. 이 수치는 단일 사용자 기록의 비교입니다. 출시 제품과 공통 시선 모델의 남은 연구를 따로 관리합니다.
